# ألعاب — بوت ديسكورد + تطبيق iOS

سطحان لنفس المنتج: بوت ألعاب جماعية عربية يرسم **كل** مخرجاته صورًا مركّبة،
وتطبيق SwiftUI يشاركه الحساب والنقاط والألعاب.

```
ios/     تطبيق SwiftUI (iOS 26+، Liquid Glass، عربي RTL بالكامل)
src/     البوت + خادم API + داشبورد الويب
```

### البناء والتحقق

**التطوير يجري على ويندوز بلا Xcode**، فالبناء والفحص البصري يجريان في
GitHub Actions على **`macos-26`** (Xcode 26.6 — Liquid Glass لا يوجد في SDK أقدم):

```bash
git push        # يشغّل .github/workflows/ios.yml
gh run download <id> -n screenshots
```

الـ workflow يبني، يشغّل اختبارات الوحدة والواجهة، **يلتقط لقطة لكل تبويب**،
ويتحقق آليًا أن المحتوى غير مقصوص من أعلى أو أسفل. دقائق macOS مجانية لأن
المستودع عام.

```bash
npm run gen:swift   # يولّد ألوان التطبيق من src/design/tokens.ts
```

مشروع Xcode **مولّد** من `ios/project.yml` بـ XcodeGen ولا يُلتزم به — ملف
`.xcodeproj` حزمة ثنائية لا تُراجَع في diff ولا تُحرَّر من غير ماك.

## الأوامر

**27 لعبة + 8 أوامر إدارة ونقاط.**

| | |
|---|---|
| **كتابة** | `اسرع` `جمع` `مفرد` `فكك` `ركب` `عكس` `عواصم` `اعلام` `قارة` `معرفه` `خمن` `ارقام` `حروف` `حساب` |
| **إقصاء** | `كت` `ايفنت` |
| **أدوار** | `xo` `حجرة` `اشبك` `نرد` `بومب` |
| **أطوار** | `مافيا` `روليت` `كراسي` `هايد` `تصويت` `غرف` |
| **نقاط** | `نقاطي` `توب` `اعطاء` |
| **إدارة** | `اعدادات` `اعدادات-الادارة` `اعدادات-الالعاب` `المالك` `ايقاف` |

كل أمر يعمل بالسلاش وبالبريفكس معًا.

```bash
npm run publish:commands
```

يُشغَّل **يدويًا** بعد إضافة أو تعديل أمر، لا عند كل إقلاع: تسجيل الأوامر العالمية
محدود بـ200 مرة يوميًا. البريفكس يعمل بلا هذا الأمر أصلًا.

> أسماء أوامر الإعدادات بشرطة لا بمسافة. ديسكورد يرفض الـ PUT **كاملًا** لو خالف
> اسم واحد قاعدته، فتسقط كل أوامر السلاش لا المخالف وحده. `slashPayload()` يصفّي
> المخالف ويطبعه بدل تمريره.

## البنية

```
src/
  design/    نظام التصميم — التوكنات والخطوط والأيقونات (يُشارَك مع الجوال)
  scenes/    وصف المشاهد وقوالبها — لا يعرف ديسكورد
  images/    تحويل المشهد إلى PNG عبر Chromium
  games/     منطق الألعاب + Table و Surface و fanout — لا يعرف ديسكورد
  discord/   العميل والأوامر واللوحات — سطح ديسكورد
  api/       خادم الجوال: OAuth، المسارات، الغرف، WebSocket — سطح الوصلة
  dashboard/ داشبورد الويب لإعدادات السيرفر
  guilds/    إعدادات السيرفر والكاش
  players/   النقاط والمحاسبة المشتركة
```

**كل لعبة مجلد مكتفٍ بذاته** فيه `game.ts` وبياناته. `games/` تُقرأ تلقائيًا عند
الإقلاع — إضافة لعبة = مجلد جديد، بلا تسجيل يدوي في أي مكان.

### القاعدة الوحيدة غير القابلة للتفاوض

`src/games/**` و`src/scenes/**` و`src/design/**` **ممنوع فيها استيراد `discord.js`**.
ESLint يكسر البناء إن حدث.

السبب أن تطبيق الجوال المخطط له يستهلك نفس هذه المجلدات كما هي. لحظة تسرّب
ديسكورد إليها يتحوّل التطبيق من «إضافة سطح» إلى «إعادة كتابة». **لا تُضعِف هذه القاعدة.**

## لعبة واحدة، عدة أسطح

`src/games/surface.ts` هو قلب اللعب عبر السطحين.

```
Surface   سطح عرض واحد: يبثّ مشهدًا ونصًا وهمسًا، ويستقبل مدخلات لاعبيه
          ├── src/discord/table.ts   قناة ديسكورد (تصير المشاهد PNG)
          └── src/api/table.ts       وصلة WebSocket (تصير مكوّنات أصلية)

fanout(surfaces) → Table   طاولة واحدة تبثّ للجميع وتدمج مدخلات الجميع
```

اللعبة لا تعرف كم سطحًا يشاهدها. `show` يذهب للكل، و`whisper(userId)` يذهب
لسطح صاحبه وحده (وللخاص في ديسكورد لمن لا تطبيق له)، و`waitChat`/`waitPress`
تُجمَّع في مصرف واحد فيفوز **أول مطابق** أيًّا كان مصدره. فشل سطح واحد (لاعب
انقطع نته) يُسجَّل ولا يوقف اللعبة، وانقطاعه يُسقطه من الجدول بدل أن ينتظره
الجميع مهلة كاملة كل جولة.

### الغرف والجسر

كل لعبة جارية هي `Session` في `games/running.ts`، سواء بدأت في قناة ديسكورد
(مفتاحها معرّف القناة) أو من الجوال وحده (مفتاحها `room:xxxx`). الجلسة تنشر
`session.join`، فمن يثبت عضويته في السيرفر ينضم إليها بسطح وصلته:

```
GET  /rooms?guildId=…        الغرف النشطة — لوبيات وألعاب جارية
ws   {"type":"rooms",  …}    نفسها عبر الوصلة
ws   {"type":"create", …}    غرفة جديدة بلا قناة ديسكورد
ws   {"type":"join", roomId} انضمام — بما فيه لعبة قائمة في قناة ديسكورد
ws   {"type":"start"}         القائد يبدأ
```

**الجسر يحتاج عملية واحدة.** سجلّ الجلسات في الذاكرة ولا يعبر حدود العمليات،
فشغّل الـ API داخل عملية البوت بـ `API_IN_PROCESS=1`. تشغيله منفصلًا
(`npm run api`) يبقى صالحًا لكل شيء عدا الانضمام لألعاب ديسكورد الجارية.

النقاط تمرّ من `src/players/settle.ts` وحدها أيًّا كان السطح — رصيد اللاعب واحد.

## التصميم

كل قيمة بصرية مصدرها [`DESIGN.md`](DESIGN.md) ثم `src/design/tokens.ts`. ممنوع hex
في أي مكان آخر.

التوقيع: حد أسود سميك + ظل صلب بلا blur، **ولون الظل يحمل معنى** — العنصر الأصفر
يُلقي ظلًا أحمر. هذا موضع اندماج لوني الهوية.

```bash
npm run preview   # يرندر كل المشاهد إلى out/ بلا ديسكورد ولا قاعدة بيانات
```

أسرع حلقة تعديل في المشروع: عدّل CSS، شغّل، انظر. لا تحتاج سيرفر تجريبي لفحص التصميم.

## لماذا متصفح وليس node-canvas

Skia و Cairo **لا يقومان بتشكيل النص**: يرسمان الجليفات ويتركان وصل الحروف لـ HarfBuzz.
النتيجة في `@napi-rs/canvas` و`node-canvas` عربي **بحروف منفصلة ومعكوسة**.

Chromium يحمل HarfBuzz و ICU bidi أصلًا، فيعطي عربيًا صحيحًا بلا عمل إضافي.
التكلفة تجمّع صفحات دائم (~300MB) و~160ms للصورة بعد الإحماء.

فخّان ظهرا فعليًا أثناء البناء وهما موثّقان في الكود:
- أسماء ديسكورد اللاتينية تنكسر داخل تخطيط RTL (`.zja6` تُعرض `zja6.`) — الحل `<bdi>`.
- `inset-inline-start` مع `translate` في RTL يدفع العنصر خارج المشهد.

## الفحص

```bash
npm run typecheck     # tsc
npm run lint          # يشمل حارس الجوال
npm test              # 77 اختبارًا: تطبيع العربية + الأسطح + جسر ديسكورد
npm run check:words   # تكرار وتشكيل ومحارف مخفية في 3084 مدخلة محتوى
npm run smoke         # كل لعبة تُحمَّل، وكل نوع مشهد له قالب يرسم
npm run dryrun        # يلعب الـ27 لعبة كاملة بطاولة وهمية، بلا ديسكورد ولا متصفح
npm run ws:play       # لعبة جماعية كاملة بوصلتين حقيقيتين على خادم حقيقي
npm run preview       # فحص بصري لكل المشاهد في out/
```

`npm run ws:play` يشغّل الخادم على منفذ حرّ، يوصل عميلَي WebSocket، ويلعب بهما
`xo` ثم `tasweet` من اللوبي حتى النتيجة طابعًا كل مشهد يصل لكل لاعب. لا يحتاج
ديسكورد ولا قاعدة بيانات ولا أسرارًا: العضوية تُزرع في الكاش من داخل العملية،
والمحاسبة تسجّل فشل قاعدة البيانات وتكمل.

**`dryrun` هو الفحص الذي يمسك ما لا يمسكه أي شيء آخر.** يشغّل كل لعبة من أولها
لآخرها على طاولة وهمية لا يجيب فيها أحد ولا يضغط أحد — وهو المسار الذي يُنسى
اختباره وفيه تكمن الحلقات التي لا تنتهي. كل لعبة لها سقف زمني، فاللعبة المعلّقة
تفشل الفحص بدل أن تجمّد البوت أمام اللاعبين.

## ملاحظات نشر

- **حالة الألعاب في الذاكرة**، وهذا صحيح مع الـ sharding لأن ديسكورد يثبّت السيرفر
  على شارد واحد (`guild_id >> 22 % shards`). لا حاجة لـ Redis.
- **التشارد** (`src/shard.ts`) لا يلزم تحت ~2000 سيرفر. وعند تفعيله **أنزل**
  `RENDER_POOL_SIZE` إلى `2`: كل شارد عملية مستقلة تشغّل Chromium خاصًا بها،
  فأربعة شاردات = أربع نسخ من المتصفح.
- **الإطفاء الآمن** يُلغي الألعاب النشطة ويعلن ذلك في قنواتها. استخدم `SIGTERM` لا `kill -9`.
- **المؤقتات تُعرض بـ `<t:unix:R>` في نص الرسالة** لا داخل الصورة. إعادة رندر صورة كل
  ثانية تضرب rate limits فورًا.
- **هوية البوت العالمية** (الاسم/الصورة/البانر) في لوحة المالك وحده. كل سيرفر يحصل
  على اسم مستعار خاص به — وإلا غيّر سيرفر واحد هوية البوت عند الجميع.
- **لا تضع المشروع داخل مجلد يزامنه OneDrive** — `node_modules` يبطئ المزامنة ويفسدها.
